# IBM BAW task dashboard — approved prototype reference

> **Status:** Approved visual and functional baseline for the `create-baw-portal` skill.  
> Do not regenerate, restyle, restructure, or replace this file.

---

## 1. Purpose

`ibm-baw-task-dashboard.html` is the initial working reference implementation for the `create-baw-portal` skill.

It serves as the canonical baseline from which all future skill-generated portals should derive their visual design contract, HTML structure, and BAW integration patterns. Any future portal generated by the skill must preserve this baseline unless the user explicitly requests a different design.

This prototype was generated from:

- The historical `baw-custom-task-list-ui` custom Bob mode

## 3. Visual Design Contract

The following characteristics define the approved visual baseline. Future generated portals must preserve these unless the user requests otherwise.

| Characteristic | Implementation detail |
|---|---|
| BAW-style full-width application shell | `html, body { height: 100%; }` with `app-body` filling remaining viewport below the fixed header |
| Compact header | `.app-header` fixed at `--header-h: 48px`, dark background `var(--ibm-gray-100)`, 14 px title text |
| High information density | 14 px base font, compact `td` padding, no card margins between sections |
| Summary cards spanning the primary workspace | `.stats-row` CSS grid of four `.stat-card` elements filling full content width |
| Compact task-search and filter toolbar | `.toolbar` single-row flex layout containing search, two selects, two buttons, and a result count |
| Structured desktop task table | Full-width `<table>` inside `.table-wrap` with five columns: Task Name, Process, Priority, Due Date, Status |
| Neutral workspace background | `body` background `var(--ibm-gray-10)` (`#f4f4f4`) |
| Clear status and priority indicators | `.priority-badge` coloured pills; `.status-badge` with `.status-dot` indicator dot |
| Minimal unused horizontal space | `.main-content` uses `padding: 24px` with no maximum-width constraint |
| Responsive reduction rather than global narrowing | `@media (max-width: 900px)` reduces `.stats-row` to 2 columns; `@media (max-width: 600px)` reduces to `1fr 1fr` and shrinks padding; table scrolls horizontally inside `.table-wrap` |
| Company branding configurable without changing information architecture | Header title is a plain `<span class="header-title">` text node — change the text without restructuring the shell |

## 4. Functional Capabilities

Capabilities that are confirmed present in the HTML source.

### Task retrieval

- Non-federated BAW task retrieval via `fetchTasksFromAPI()` using the WLE REST API
- Tasks are fetched on page load via the `init()` IIFE and on manual refresh via the **↻ Refresh** button

### Task rendering

- Current (actionable) tasks rendered in the `taskTableBody` `<tbody>`
- Non-actionable states (`finished`, `terminated`, `completed`, `closed`, `failed`) filtered out client-side in `loadTasks()`
- Task name displayed as a clickable `<a class="task-name-link">` link
- Process name displayed in `.process-name` with `title` tooltip for overflow
- Priority displayed as a coloured `.priority-badge` (high / medium / low)
- Due date displayed as a human-friendly relative string (e.g. "2d overdue", "Due in 4h", "Tomorrow") with colour class (`due-overdue`, `due-atrisk`, `due-ok`)
- Status displayed as a `.status-badge` with a coloured `.status-dot` and normalised label

### Summary cards

- **Overdue** count (`#statOverdue`) — tasks where due date is in the past
- **At Risk** count (`#statAtrisk`) — tasks due within 24 hours
- **Active** count (`#statActive`) — tasks where normalised state equals `claimed`
- **All Tasks** count (`#statAll`) — total actionable task count
- Cards are computed client-side by `computeStats()` after each fetch

### Filtering

| Filter | Mechanism |
|---|---|
| Stat-card filter | `setFilter(filter)` sets `state.currentFilter`; active card marked with `.active-filter` and `aria-pressed` |
| Search | `#searchInput` (`type="search"`) calls `handleSearch()` → `applyFilters()`. Searches fields `TAD_DISPLAY_NAME`, `NAME`, `PT_NAME`, `TAD_DESCRIPTION` |
| Priority dropdown | `#priorityFilter` `<select>`, values `high` / `medium` / `low`, matched via `priorityLabel()` |
| Status dropdown | `#statusFilter` `<select>`, values `claimed` / `ready` / `received`, matched via `normState()` |
| Clear all | `clearAllFilters()` resets all inputs, restores `all` stat-card, calls `applyFilters()` |

### Sorting

- `sortBy(field)` toggles `asc`/`desc` on repeated clicks; fields: `name`, `priority`, `due`
- `sortTasks()` sorts `state.filteredTasks` in-place and updates `th[aria-sort]` and `.sort-indicator` text on `#th-name`, `#th-priority`, `#th-due`
- Default sort: `due` ascending

### Pagination

- `PAGE_SIZE = 10` rows per page
- `renderPagination(pages, total)` renders prev/next buttons and up to 7 numbered page buttons with ellipsis via `pageRange()`
- `goPage(p)` updates `state.currentPage` and scrolls `.table-wrap` into view
- `#paginationBar` displays current range label (e.g. "1–10 of 34") and navigation buttons

### Refresh

- **↻ Refresh** button (`btn-primary`) calls `loadTasks()` directly
- No automatic polling is implemented

### Task opening

- `openTask(taskId, taskName)` constructs URL `/teamworks/process.lsw?zWorkflowState=1&zTaskId=<id>&zResetContext=true`
- Opens task in `#taskIframe` inside `#taskModal`
- Modal title set to task name via `#modalTitle`

### Task modal

- `#taskModal` (`role="dialog"`, `aria-modal="true"`, `aria-labelledby="modalTitle"`)
- Closed by: close button (`closeModal()`), Escape key (`document.addEventListener('keydown')`), backdrop click (`handleBackdropClick`)
- iframe `src` reset to `about:blank` on close

### Toast notifications

- `toast(msg, type)` — appends a `.toast` div to `#toastContainer` (`aria-live="assertive"`), auto-removes after 4 000 ms
- Types: `info` (blue left-border), `error` (red left-border)
- Currently triggered only on fetch failure

## 5. BAW Integrations

### Non-federated BAW (WLE REST API)

Both endpoints use `credentials: 'same-origin'` (session cookie authentication).

#### Task list endpoint

```
GET /rest/bpm/wle/v1/tasks?calcStats=true&size=500&offset=0&filterByCurrentUser=true&includeAllBusiness=true
```

| Parameter | Value | Purpose |
|---|---|---|
| `calcStats` | `true` | Request server-side statistics (not yet consumed; client computes its own) |
| `size` | `500` | Page-size for the server call — prototype loads all tasks in one request |
| `offset` | `0` | Zero-based start offset |
| `filterByCurrentUser` | `true` | Restrict to tasks assigned to the authenticated user |
| `includeAllBusiness` | `true` | Include all business task types |

Request headers: `Accept: application/json`, `Content-Type: application/json`.

#### Current user endpoint

```
GET /rest/bpm/wle/v1/user/current?parts=all
```

Used by `loadUser()` to populate `#userName` and `#userAvatar`. Fields consumed:
- `data.fullName` (preferred)
- `data.displayName` (fallback)
- `data.userName` (fallback)

#### Task-launch URL pattern

```
/teamworks/process.lsw?zWorkflowState=1&zTaskId=<TKIID>&zResetContext=true
```

Constructed in `openTask()`. `taskId` value sourced from `task.TKIID`.

### Federated BAW (Process Federation Server)

The prototype does **not** use PFS federated APIs. Future portal generation must distinguish between:

| Environment | API base | Task list endpoint |
|---|---|---|
| Non-federated BAW | BAW server directly | `/rest/bpm/wle/v1/tasks` |
| Federated BAW with PFS | PFS server | `/rest/bpm/federated/v1/tasks` (different response shape, system IDs required) |

The skill must prompt for environment type and generate appropriate integration code for each.

## 6. Verified Response Structure

The following documents the task response structure observed in the working non-federated environment and used by this prototype. **These field names are not guaranteed to be universal across all BAW versions or configurations.**

### Top-level response envelope

```json
{
  "status": "200",
  "data": { ... }
}
```

The prototype handles multiple shapes in `loadTasks()`:

| Shape | Handled |
|---|---|
| Top-level array | `Array.isArray(json)` |
| `json.items` array | `Array.isArray(json.items)` |
| `json.data.items` array | `Array.isArray(json.data?.items)` |
| `json.data` array | `Array.isArray(json.data)` |

### `data.items` — task fields actually used

| Field | Used by | Notes |
|---|---|---|
| `TKIID` | `openTask()`, `renderTable()` | Task instance ID; used to construct the launch URL |
| `TAD_DISPLAY_NAME` | `renderTable()`, `applyFilters()`, `sortTasks()` | Preferred human-readable task name |
| `NAME` | `renderTable()`, `applyFilters()`, `sortTasks()` | Fallback task name |
| `PT_NAME` | `renderTable()`, `applyFilters()` | Process template (process) name |
| `TAD_DESCRIPTION` | `applyFilters()` | Searched but not displayed |
| `PRIORITY` | `priorityLabel()`, `sortTasks()`, `applyFilters()` | Numeric 10–50; ≥40 = high, 21–39 = medium, ≤20 = low |
| `DUE` | `parseDue()`, `dueStatus()`, `formatDue()`, `computeStats()` | ISO 8601 date string |
| `STATE` | `normState()`, `loadTasks()`, `applyFilters()` | Prefixed with `State_` (e.g. `State_claimed`); stripped by `normState()` |
| `STATUS` | `normState()`, `loadTasks()` | Alternative status field; same `State_` prefix convention |

### State values observed

BAW prefixes state values with `State_`. The prototype normalises them by stripping the prefix:

| Raw value | Normalised | Used for |
|---|---|---|
| `State_claimed` | `claimed` | Active count; status badge |
| `State_ready` | `ready` | Status badge |
| `State_received` | `received` | Status badge |
| `State_finished` | `finished` | Excluded from task list |
| `State_terminated` | `terminated` | Excluded from task list |

### `data.stats` and `data.attributeInfo`

These fields are present in the API response (requested via `calcStats=true`) but are **not consumed** by the prototype. Stats are computed entirely client-side in `computeStats()`.

## 7. Reusable patterns

The following implementation patterns are candidates for extraction into the `create-baw-portal` skill's generated output.

| Pattern | Location | Description |
|---|---|---|
| Centralised endpoint configuration | `fetchTasksFromAPI()` | Single `fetch()` call with query string; easy to extract URL and params as named constants |
| Centralised task-response extraction | `loadTasks()` — the four `Array.isArray` checks | Handles server response shape variations in one place before any other code sees the data |
| Centralised task normalisation | `normState(task)` | Strips `State_` prefix from `task.STATE \|\| task.STATUS`; single function consumed by filters, renderer, and stats |
| Task filtering | `applyFilters()` | Chains stat-card, search, priority, and status filters against `state.allTasks` into `state.filteredTasks` |
| Priority normalisation | `priorityLabel(val)` | Maps numeric `PRIORITY` (10–50) to string `high` / `medium` / `low` |
| Due-date classification | `dueStatus(due)` | Returns `'overdue' \| 'atrisk' \| 'ok' \| 'none'`; threshold at `MS_DAY` (86 400 000 ms) |
| Safe task rendering | `escHtml(str)` | HTML-escapes `&`, `<`, `>`, `"` before inserting task data into `innerHTML` |
| Task sorting | `sortBy(field)` + `sortTasks()` | Toggle-direction sort on `name`, `priority`, `due`; updates `th[aria-sort]` and `.sort-indicator` |
| Pagination | `renderPagination()` + `pageRange()` + `goPage()` | Client-side pagination at `PAGE_SIZE = 10`; ellipsis page range; smooth scroll to `.table-wrap` |
| Task-launch handling | `openTask(taskId, taskName)` | Constructs `/teamworks/process.lsw` URL, sets `#taskIframe` src, opens `#taskModal` |
| Theme variables | `:root` CSS custom properties | Full IBM colour palette, `--radius`, `--shadow-sm/md`, `--transition`, `--header-h` centralised in `:root` |

## Readiness for targeted hardening

The prototype implements a functionally complete non-federated BAW task portal with correct API integration, client-side filtering, sorting, pagination, task launching, and meaningful loading, error, and empty states.

The highest-priority hardening targets before promotion to a production template are:

1. **Security** — add `sandbox` attribute to `#taskIframe`; review CSRF posture
2. **Accessibility** — add focus trap and focus-return to `#taskModal`; add skip-navigation link
3. **Refresh safety** — disable **↻ Refresh** during in-flight fetch
4. **Mobile** — add card-based task layout below a narrow breakpoint

The prototype is ready for targeted hardening on these specific items. It does not require a structural rewrite.
