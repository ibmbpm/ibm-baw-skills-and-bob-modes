# Service Flow Test Suite Format

This is the canonical structure for all test suites generated by the `test-baw-service-flows` skill.
Both Phase A (generation) and Phase B (execution) read this format. Treat it as the contract between the two phases.

---

## Top-level structure

```json
{
  "schema_version": "1.0",
  "app": {
    "name": "Human-readable process application name",
    "acronym": "ACRONYM",
    "snapshot": "SNAP_ACRONYM"
  },
  "service_flow": {
    "name": "Exact Service Flow name as authored in BAW",
    "service_id": "serviceId for direct WLE v1 invocation (null if not applicable)",
    "automation_service_path": "/path from the OpenAPI spec (null if not applicable)",
    "process_model": "Process model name for fallback invocation (null if not applicable)",
    "exposure_type": "automation_service | startable | process_embedded"
  },
  "generated_at": "ISO-8601 timestamp",
  "test_cases": [ /* array of test case objects — see below */ ]
}
```

---

## Test case object

```json
{
  "id": "SFTC-001",
  "name": "Short human-readable name",
  "path": "happy | error | validation | boundary | edge",
  "description": "One or two sentences describing what this test validates.",
  "input": {
    "description": "What this input combination is testing",
    "data": {
      "field_name": "value"
    }
  },
  "expected_status": "success | error",
  "expected_output": {
    "field_name": "expected_value | any | any_non_null | >= N | contains:substring"
  },
  "expected_error": {
    "http_status": 400,
    "code": "BPMVALIDATION001 | any",
    "message_contains": "substring of the expected error message | any"
  },
  "tags": ["optional", "labels"]
}
```

**Field rules:**
- `expected_status` must be `"success"` or `"error"`. Choose `"error"` for any test designed to trigger a fault, validation rejection, or non-2xx response.
- `expected_output` is only evaluated when `expected_status` is `"success"`. Leave as `{}` for error tests.
- `expected_error` is only evaluated when `expected_status` is `"error"`. Leave as `{}` for success tests.
- At least one of `expected_output` or `expected_error` must be non-empty.
- Use `"any"` as a value in `expected_output` or for `expected_error.code`/`message_contains` when the exact value is not predictable but the field must exist.
- Use `"any_non_null"` when the value must exist and be non-null but the exact value is not asserted.
- Use range operators (`">= 0"`, `"< 100"`, `"== 42"`) for numeric assertions.
- Use `"contains:<substring>"` for partial string matching.

---

## Path labels

Use exactly these values for `path`:

| Value | Meaning |
|---|---|
| `happy` | Minimal valid call — all required inputs, representative values, expects a successful response. |
| `error` | Designed to trigger a declared fault or documented error code from the service. |
| `validation` | Designed to trigger an input validation error (missing required field, wrong type, out-of-range value). |
| `boundary` | At the edge of a valid input range (exactly at minimum or maximum allowed value). |
| `edge` | An unusual but technically valid scenario (empty array, null optional field, special characters, same-day dates). |

---

## ID naming convention

| Prefix | Meaning |
|---|---|
| `SFTC-001` | Happy path (and additional happy-path variants) |
| `SFTC-ERR-001` | Declared fault / documented error path |
| `SFTC-VAL-001` | Input validation error path |
| `SFTC-BND-001` | Boundary value test |
| `SFTC-EDGE-001` | Edge case |

IDs must be unique across the entire test suite.

## Minimal example

```json
{
  "schema_version": "1.0",
  "app": {
    "name": "Claim Processing",
    "acronym": "CP",
    "snapshot": "CPV200"
  },
  "service_flow": {
    "name": "Calculate Claim Amount",
    "service_id": null,
    "automation_service_path": "/ClaimProcessing/CalculateClaimAmount",
    "process_model": null,
    "exposure_type": "automation_service"
  },
  "generated_at": "2026-08-15T10:00:00Z",
  "test_cases": [
    {
      "id": "SFTC-001",
      "name": "Happy path — valid claim with standard deductible",
      "path": "happy",
      "description": "A claim with a valid policy number and incurred amount produces a calculated payout.",
      "input": {
        "description": "Minimal valid claim data",
        "data": {
          "policyNumber": "POL-12345",
          "incurredAmount": 5000,
          "claimType": "medical"
        }
      },
      "expected_status": "success",
      "expected_output": {
        "payoutAmount": ">= 0",
        "status": "approved",
        "calculationId": "any_non_null"
      },
      "expected_error": {},
      "tags": ["smoke"]
    },
    {
      "id": "SFTC-VAL-001",
      "name": "Missing required field — policyNumber absent",
      "path": "validation",
      "description": "Omitting the required policyNumber field should return a validation error.",
      "input": {
        "description": "policyNumber omitted",
        "data": {
          "incurredAmount": 5000,
          "claimType": "medical"
        }
      },
      "expected_status": "error",
      "expected_output": {},
      "expected_error": {
        "http_status": 400,
        "code": "any",
        "message_contains": "policyNumber"
      },
      "tags": []
    },
    {
      "id": "SFTC-BND-001",
      "name": "Boundary — incurredAmount at minimum (0)",
      "path": "boundary",
      "description": "incurredAmount of 0 is at the declared minimum. Service should accept it and return 0 payout.",
      "input": {
        "description": "incurredAmount set to exactly 0",
        "data": {
          "policyNumber": "POL-12345",
          "incurredAmount": 0,
          "claimType": "medical"
        }
      },
      "expected_status": "success",
      "expected_output": {
        "payoutAmount": 0,
        "status": "approved"
      },
      "expected_error": {},
      "tags": []
    }
  ]
}
```

## Human-readable output format (`output/<acronym>/<acronym>-sf-test-suite.md`)

At the end of Phase A, produce this markdown file alongside the JSON in the same `output/<acronym>/` directory.

### File structure

```markdown
# Service Flow Test Suite — <App Name> (<ACRONYM>) · <Snapshot>
Service Flow: <Service Flow name>   |   Exposure: <exposure_type>
Generated: <ISO timestamp>

## Summary

| ID | Name | Path | Inputs used |
|----|------|------|-------------|
| SFTC-001 | Happy path — valid claim | happy | policyNumber, incurredAmount, claimType |
| SFTC-VAL-001 | Missing policyNumber | validation | incurredAmount, claimType |
| ... | ... | ... | ... |

---

## SFTC-001 · Happy path — valid claim with standard deductible

**Path:** happy

**Description:** A claim with a valid policy number and incurred amount produces a calculated payout.

**Input:**
- `policyNumber`: "POL-12345"
- `incurredAmount`: 5000
- `claimType`: "medical"

**Expected outcome:**
- Status: `success`
- `payoutAmount`: >= 0
- `status`: "approved"
- `calculationId`: any non-null value

---

## SFTC-VAL-001 · Missing required field — policyNumber absent
...
```

### Rules for the markdown file

- One `##` section per test case, labelled `SFTC-NNN · <name>`.
- The summary table at the top lists every test case — this is what a reviewer scans first.
- Show only the inputs actually used (omitted fields are implicitly absent).
- Express expected output assertions in plain English — do not show operator syntax verbatim (for example, write "any non-null value" not `"any_non_null"`).
- Keep language plain — readable by QA engineers and business analysts, not just developers.
